# Channel Profile Avatar Implementation Plan

## Overview

Give the channel profile a visual identity: the user either uploads an image or generates one from their saved `niche` and `sub_niche`. The avatar lives in a private, per-owner Supabase Storage bucket and is shown in the app shell. This is roadmap slice S-05, delivering PRD FR-015.

## Current State Analysis

- `channel_profiles` has `id`, `user_id`, `niche`, `sub_niche`, `competitors`, `created_at`, `updated_at` — **no avatar column** (`supabase/migrations/20260909213911_create_channel_profiles.sql`, `supabase/migrations/20260912190947_competitors_as_objects.sql`).
- `supabase.storage` is **never called** anywhere in `src/` or `supabase/`, and no `storage.objects` policy exists. The service is enabled locally (`supabase/config.toml:114-117`) with no bucket declared.
- There is **no binary or file handling anywhere in the codebase**. The only `formData()` calls read text fields in `src/pages/api/auth/*`.
- The profile is read server-side in `src/components/Topbar.astro:8-15` and hydrated as `<ProfileDialog client:load />` (`:29`). There is no `GET /api/profile`.
- `src/components/ui/` holds only `LibBadge.astro`, `button.tsx`, `card.tsx`, `dialog.tsx`, `skeleton.tsx`, `sonner.tsx` — no `avatar`.
- `wrangler.jsonc` declares `ASSETS` and a `RATE_LIMITER` ratelimit binding; there is no `ai` binding. `worker-configuration.d.ts` is committed and generated by `npx wrangler types`.
- No service-role Supabase client exists — `src/lib/supabase.ts` exports one cookie-scoped `createClient(headers, cookies)` that returns `null` when unconfigured.

## Desired End State

A signed-in user with a saved profile opens the profile dialog and either uploads an image or clicks Generate. Either way a 512×512 avatar appears in the dialog and in the topbar within seconds, is stored under `avatars/<user_id>/`, and is unreadable by any other user. The user can replace it or remove it. With the `AI` binding absent the Generate button is not rendered and upload continues to work unchanged.

**Verification**: the Phase 3 checkpoint *is* the degraded state FR-015 requires, so upload-only correctness is proven before generation exists. Owner isolation is proven by a two-user Storage REST check, replicating the F-02 protocol (`context/changes/channel-profile-data-model/plan.md:170-179`).

### Key Discoveries:

- **`avatar_url` is the wrong contract.** Private buckets are read via `createSignedUrl`, which expires; a persisted URL would rot. The column stores the **object path** and is therefore named `avatar_path`. This deviates from the PRD's wording at `context/foundation/prd.md:127` — recorded in `change.md`.
- **`FormData` is a known landmine here.** S-01 tried it and abandoned it because a browser extension clobbered the global constructor (`context/changes/channel-profile-crud/plan.md:32`). Binary bytes cannot go through JSON, so the upload sends a **raw request body** read with `request.arrayBuffer()` — no `FormData` on either side.
- **React 19 form actions do not work inside a Radix `Dialog`** (`context/changes/channel-profile-crud/plan.md:31`), which is exactly where this UI lives. Use plain handlers and `SubmitButton`'s existing `pending` prop, as `ChannelProfileForm.tsx:61-93` does.
- **No resizing is available server-side.** Supabase transforms are Pro-only (`supabase/config.toml:131-133`) and the free-tier 10ms CPU cap plus `sharp`'s workerd incompatibility rule out in-Worker work (`context/foundation/infrastructure.md:55,87`). Normalization happens on the client canvas, and generation requests 512×512 directly.
- **Bindings, not secrets.** `src/pages/api/analyze.ts:15,56` establishes `import { env } from "cloudflare:workers"`. Workers AI extends it, so this slice adds **no new secret** — no `.dev.vars`, no CI `env:` entry, no `wrangler secret put`.
- **RLS-first.** The cookie-scoped client can write into the caller's own folder under RLS, so neither upload nor generation needs a service-role client.

## What We're NOT Doing

- No public bucket, no CDN-cacheable avatar URL.
- No avatar history or undo — a replaced object is deleted.
- No server-side or in-Worker image processing of any kind.
- No moderation model in front of the generation prompt.
- No Supabase mocking or API-route tests — DB and storage paths are verified manually, per project precedent (`context/changes/analyze-and-rank-opportunities/plan.md:412-414`).
- No avatar on any surface other than the profile dialog and the topbar.
- No changes to competitor handling, analysis, or auth.

## Implementation Approach

Build outward from the data layer, keeping every provider-dependent decision in the last phases. Phases 1–3 depend only on Supabase and ship a complete upload feature; Phase 4 adds generation on top. The single unverified assumption — whether the Workers AI binding is reachable under `astro dev` — is therefore contained: if it fails, the slice has already delivered working value and FR-015's fallback behaviour.

## Critical Implementation Details

**Write ordering on replace.** The new object must be uploaded and `avatar_path` updated *before* the superseded object is deleted. The reverse order loses the user's avatar entirely if the upload then fails, and a failed delete must never roll back a successful path update — an orphaned object is recoverable, a lost pointer is not.

**Signed URLs start their clock at SSR render, not at image paint.** Minting in `Topbar.astro` means the ~1h window is consumed by how long the tab stays open, not by how long the image is displayed.

## Phase 1: Data layer

### Overview

Add the column, the bucket, and the owner-scoped storage policies in one migration, then regenerate types.

### Changes Required:

#### 1. Migration

**File**: `supabase/migrations/<YYYYMMDDHHmmss>_add_channel_profile_avatar.sql`

**Intent**: Add nullable avatar storage to the profile and create a private bucket whose objects are readable and writable only by the user whose id names their top-level folder. Replicates the four-policy shape from F-02 rather than a single `for all` policy, per `context/foundation/roadmap.md:184`.

**Contract**: `channel_profiles.avatar_path text` (nullable). Bucket `avatars`: `public = false`, `file_size_limit` 2 MiB, `allowed_mime_types` limited to PNG/JPEG/WebP. Four policies on `storage.objects` — `avatars_select_own`, `avatars_insert_own`, `avatars_update_own`, `avatars_delete_own` — all `to authenticated`, `using` for select/delete, `with check` for insert, both for update, each predicated on:

```sql
bucket_id = 'avatars' and (select auth.uid()::text) = (storage.foldername(name))[1]
```

The bucket is created in SQL (not `config.toml`) so the same definition applies locally and in the hosted project.

#### 2. Generated types

**File**: `src/lib/database.types.ts`

**Intent**: Regenerate so `avatar_path` is typed. Never hand-edited.

**Contract**: `npm run db:types`. `ChannelProfile` in `src/lib/services/channel-profile.ts:26` is `Omit<Row, "competitors">`, so the new field flows through `parseChannelProfile` with no code change. Note that `supabase gen types` covers tables only — storage policies get no generated types, which is why their correctness is established manually below.

### Success Criteria:

#### Automated Verification:

- Migration applies cleanly: `npx supabase db reset`
- Types regenerate and `git diff src/lib/database.types.ts` shows `avatar_path`
- Linting passes: `npm run lint`

#### Manual Verification:

- Bucket `avatars` exists in Supabase Studio, marked private, with the size and MIME limits applied
- All four policies are present on `storage.objects`
- Two-user isolation: with user B's JWT, reading, overwriting and deleting an object under user A's folder all fail via the Storage REST API

## Phase 2: Pure service module

### Overview

Establish the shared bounds and pure helpers before any I/O, following the sequencing S-02 used (`context/changes/analyze-and-rank-opportunities/plan.md:56-66`).

### Changes Required:

#### 1. Avatar service

**File**: `src/lib/services/avatar.ts`

**Intent**: Own the validation bounds, the prompt template and the object-path scheme as pure, I/O-free functions. Exported constants are imported by *both* the route and the client component, so the client/server validation mirror that impl-review F1 flagged is enforced by construction rather than by discipline. Must not import `astro:env/server` or call `fetch`, per the convention documented at `src/lib/services/scoring.ts:4`.

**Contract**: exports `MAX_AVATAR_BYTES`, `ALLOWED_AVATAR_TYPES`, `AVATAR_EDGE_PX` (512); `validateAvatarUpload({ contentType, byteLength })` returning a discriminated result carrying the resolved file extension or a user-facing message; `buildAvatarPrompt(niche, subNiche)` slotting **truncated** user text into a fixed style template rather than concatenating it; `avatarObjectPath(userId, extension)` returning `<userId>/<uuid>.<ext>` so each write gets a fresh path and no stale image is ever served from cache.

#### 2. Unit tests

**File**: `src/lib/services/avatar.test.ts`

**Intent**: Cover the bounds and the prompt template. Matches the existing `include: ["src/lib/services/**/*.test.ts"]` glob in `vitest.config.ts`, so no config change.

**Contract**: cases at, under and over `MAX_AVATAR_BYTES`; each allowed MIME type and at least one rejected type; `buildAvatarPrompt` truncates over-long niche text and produces a prompt where the user text cannot escape the template.

### Success Criteria:

#### Automated Verification:

- Unit tests pass: `npm test`
- Linting passes: `npm run lint`

#### Manual Verification:

- Prompts built from two or three real niches read sensibly as image prompts

## Phase 3: Upload end-to-end

### Overview

A complete, shippable avatar feature. On completion the app is in exactly the state FR-015 requires when generation is unavailable.

### Changes Required:

#### 1. Avatar route

**File**: `src/pages/api/avatar.ts`

**Intent**: Accept a raw image body, store it under the caller's folder, point the profile at it, and delete whatever it replaced. `DELETE` clears the avatar and removes the object. Writes go through the existing cookie-scoped client so RLS — not application logic — enforces ownership.

**Contract**: `POST` reads `request.arrayBuffer()` inside a try/catch returning a 400 JSON envelope (impl-review F3) and takes the MIME type from the `Content-Type` header; **no `FormData`**. Self-checks `context.locals.user` and returns 401 when absent — `PROTECTED_ROUTES` covers pages only (CLAUDE.md; impl-review F8). Validates via `validateAvatarUpload`, uploads to `avatarObjectPath(...)`, updates `channel_profiles.avatar_path`, then deletes the previous object. Responds `{ avatar_path, avatar_url }` where `avatar_url` is freshly signed. `DELETE` reverses it. All errors use `jsonError` from `src/lib/http.ts`.

#### 2. Topbar read

**File**: `src/components/Topbar.astro`

**Intent**: Sign a URL for the stored path alongside the profile read already happening at `:8-15`, and render the avatar. A *failed* signing must stay distinguishable from "no avatar", mirroring the `loadFailed` handling that impl-review F4 introduced — the write path replaces the object, so a misread must not invite a destructive overwrite.

**Contract**: signed URL minted with ~1h expiry when `profile?.avatar_path` is set; passes `initialAvatarUrl` and an `avatarLoadFailed` flag into `<ProfileDialog />`.

#### 3. Avatar field

**File**: `src/components/profile/AvatarField.tsx` (new), plus `npx shadcn@latest add avatar`

**Intent**: Show the current avatar, let the user pick a file, normalize it to 512×512 on a canvas before sending, and offer Remove. Plain `onChange`/`onClick` handlers — **not** a React 19 form `action`, which is broken inside Radix `Dialog`.

**Contract**: imports its size and type bounds from `src/lib/services/avatar.ts` rather than restating them. Resizes to `AVATAR_EDGE_PX` square on canvas, then `fetch`es the resulting blob as a raw body. Every `fetch` uses try/catch/finally, not just finally (impl-review F2). Errors render through the existing `src/components/auth/ServerError.tsx`; pending state uses `SubmitButton`'s `pending` prop.

#### 4. Dialog wiring

**File**: `src/components/profile/ProfileDialog.tsx`

**Intent**: Render `AvatarField` above `ChannelProfileForm`, driven by the `profile` state the component already holds at `:13`.

**Contract**: accepts `initialAvatarUrl` and `avatarLoadFailed` props; keeps its existing `onSaved` behaviour untouched.

### Success Criteria:

#### Automated Verification:

- Linting passes: `npm run lint`
- Unit tests still pass: `npm test`
- Production build succeeds: `npm run build`

#### Manual Verification:

- Uploading a PNG shows the avatar in the dialog and topbar; the object appears under `avatars/<user_id>/` in Supabase Studio
- An oversized file and a `.pdf` are both rejected in the browser **and** by the route when posted directly with `curl`
- Re-uploading replaces the image, the previous object is gone, and no stale image is served
- Remove clears the avatar and deletes the object
- A signed-out request for the raw object path is refused

## Phase 4: AI generation

### Overview

Add the Workers AI binding and an on-demand, rate-limited Generate action. Begin by confirming `env.AI.run` is reachable under `npm run dev` — everything else in this phase depends on it.

### Changes Required:

#### 1. Binding

**File**: `wrangler.jsonc`, `worker-configuration.d.ts`

**Intent**: Declare the Workers AI binding and a second rate-limit namespace guarding generation cost, then regenerate the committed worker types.

**Contract**: add `"ai": { "binding": "AI" }` and an `AVATAR_LIMITER` entry in `ratelimits` (5 per 60s; `period` accepts only 10 or 60). Run `npx wrangler types` so `AI: Ai` joins `RATE_LIMITER: RateLimit` in `__BaseEnv_Env`. If the binding proves unreachable under `astro dev`, try the adapter's `remoteBindings` option before considering another provider — the fallback documented in research is fal.ai-hosted FLUX schnell over plain `fetch`.

#### 2. Generation in the service module

**File**: `src/lib/services/avatar.ts`

**Intent**: Add the generation call as a typed result that never throws, mirroring `JustifyResult` in `src/lib/services/justify.ts:61`. The binding is **passed in as a parameter**, keeping the module free of framework and platform imports.

**Contract**: `generateAvatar(ai, prompt)` → `{ ok: true; bytes } | { ok: false; message }`, requesting `@cf/black-forest-labs/flux-1-schnell` at 512×512. Decode whatever shape the model returns — expected to be JSON with a base64 `image` field, unlike the older Stable Diffusion models which return a `ReadableStream`; confirm against the model page during the spike.

#### 3. Generate route

**File**: `src/pages/api/avatar/generate.ts`

**Intent**: Build a prompt from the caller's saved profile, generate, and store the result through the same write path as an upload.

**Contract**: 401 self-check, then `AVATAR_LIMITER.limit({ key: user.id })` returning 429 on refusal, matching `src/pages/api/analyze.ts:56`. Returns 409 when no profile exists — generation reads `niche`/`sub_niche` server-side. Returns 503 naming the missing capability when `env.AI` is absent. Reuses Phase 3's store-and-replace logic so ordering and cleanup are not duplicated.

#### 4. Generate control

**File**: `src/components/profile/AvatarField.tsx`, `src/components/Topbar.astro`

**Intent**: Offer generation only when it can actually work. Deliberately **not** added to `src/lib/config-status.ts`: that module reads secrets from `astro:env/server` at module scope and there is no secret here — binding presence is a per-request fact. `Topbar.astro` checks `env.AI` at request time and passes a flag down, so the button is hidden rather than offered-then-broken.

**Contract**: `canGenerate` prop threaded from `Topbar.astro`; the button is disabled while no profile is saved, and a failed generation leaves the existing avatar untouched and surfaces the message through `ServerError`.

#### Automated Verification:

- `npx wrangler types` regenerates cleanly and `AI` is typed; `npm run lint` passes
- Production build succeeds: `npm run build`
- Unit tests still pass: `npm test`

#### Manual Verification:

- `env.AI.run` is reachable under `npm run dev`, and the response shape is confirmed
- Generate produces a niche-derived 512×512 avatar within a few seconds
- A sixth generation inside a minute returns 429

## Testing Strategy

### Unit Tests:

- `validateAvatarUpload` at, under and over the byte cap; every allowed MIME type; at least one rejected type
- `buildAvatarPrompt` truncation and template containment — user text must not be able to escape the template
- `avatarObjectPath` produces a distinct path per call under the caller's folder

### Integration Tests:

None. Route and storage behaviour is verified manually, consistent with every prior slice — there is no Supabase mocking convention in this repo and this plan does not establish one.

### Manual Testing Steps:

1. `npx supabase db reset && npm run db:types`; confirm `avatar_path` appears in the generated types
2. Sign in, open the profile dialog, upload a PNG; confirm it renders in the dialog and topbar
3. Confirm the object landed under `avatars/<user_id>/` in Supabase Studio
4. Attempt an oversized file and a `.pdf` in the browser, then repeat with `curl` directly against the route
5. Re-upload; confirm the old object is gone and the new image renders immediately
6. Remove; confirm the avatar clears and the object is deleted
7. With user B's JWT, attempt select, update and delete on user A's object path via the Storage REST API — all four must fail
8. Click Generate; confirm a niche-derived image within a few seconds; repeat six times to trigger 429
9. Remove the `ai` binding, restart, and confirm upload still works with no Generate button

## Performance Considerations

Client-side normalization to 512×512 keeps stored objects at roughly 50–100 KB, so the topbar avatar costs a small signed-URL fetch rather than a multi-megabyte download. Generation at 512 rather than 1024 also cuts the cost per image from 57.6 to 43.2 neurons (~$0.00048), leaving the 10,000 neuron/day free allocation good for roughly 230 generations per day. No image bytes are processed in the Worker, so the 10 ms free-tier CPU budget is spent only on request handling and the Supabase round trip — confirmed against Workers Logs in Phase 5.

## Migration Notes

One new migration, additive and nullable: existing profiles keep working with `avatar_path` null, which renders as no avatar. Rollback is `alter table ... drop column avatar_path` plus dropping the four policies and the bucket; objects in the bucket are lost on bucket deletion, which is acceptable for a nice-to-have feature with no other consumers. Phase 5 is the project's first `supabase db push`, so expect all three migrations to apply to a hosted project that currently has none of them.
